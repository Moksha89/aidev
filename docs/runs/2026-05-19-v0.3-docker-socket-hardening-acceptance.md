# 2026-05-19 — Ubuntu GPU VPS — v0.3 Docker socket hardening acceptance run

PR: [#6 feat(sandbox): v0.3 Docker socket gatekeeper via tecnativa/docker-socket-proxy](https://github.com/Moksha89/aidev/pull/6) ·
branch `devin/v0.3-docker-socket-hardening` · commit `f47d050`.

Acceptance probe: `workers/sandbox-runner/scripts/pass2_docker.py`
with the new v0.3 section 0a, executed inside `infra-sandbox-runner-1`
against the live `docker-socket-proxy:2375` and the host Docker
daemon. 14 sections / 64 assertions **PASS**.

## What changed since PR #5 acceptance

- The `sandbox-runner` container no longer bind-mounts
  `/var/run/docker.sock`. A bug/compromise in the worker no longer
  equals root on the host.
- A new `docker-socket-proxy` service
  (`tecnativa/docker-socket-proxy:0.2.0`) is the only container that
  still binds the host socket — and it binds it **read-only**.
- The worker connects via `DOCKER_HOST=tcp://docker-socket-proxy:2375`
  on the internal compose network. The proxy's port `2375` is not
  published on the host (no UFW change needed).
- The proxy enforces an explicit allow/deny matrix on the Engine API:
  - Allowed: `PING`, `VERSION`, `CONTAINERS`, `NETWORKS`, `VOLUMES`,
    `EXEC`, `IMAGES`, `POST`.
  - Blocked (returns HTTP 403): `AUTH`, `BUILD`, `COMMIT`, `CONFIGS`,
    `DISTRIBUTION`, `EVENTS`, `INFO`, `NODES`, `PLUGINS`, `SECRETS`,
    `SERVICES`, `SESSION`, `SWARM`, `SYSTEM`, `TASKS`.
- Proxy hardening: `cap_drop: [ALL]`,
  `security_opt: [no-new-privileges:true]`, no host port, host
  socket bound `:ro`. (`read_only: true` on the rootfs is
  intentionally NOT set — see `docs/SECURITY.md` for the rationale.)
- v0.2 dual-network design (`internal: true` sandbox bridge +
  plain pub bridge + forwarder sidecar + per-task egress-proxy
  attachment) is unchanged.

## Test environment

- Host: Ubuntu Server 24 LTS, same single-tenant box as PR #4 / #5.
- Stack: `devin/v0.3-docker-socket-hardening` @ commit `f47d050`,
  built locally on the host and brought up with
  `docker compose -f infra/docker-compose.yml --env-file infra/.env up -d`.
- Probe: `pass2_docker.py` is now baked into the worker image
  (`docker/Dockerfile.worker` copies `workers/${WORKER}/scripts`),
  so the probe runs in-image via
  `docker exec --user 0 -w /app -e PYTHONPATH=/app infra-sandbox-runner-1 python /app/scripts/pass2_docker.py`.

## Remaining risks (not fixed by v0.3)

1. **Misuse of an allowed endpoint.** The proxy lets the worker
   create containers; an attacker who controls the worker process
   can still `POST /containers/create` with
   `HostConfig.Privileged: true`, or with arbitrary bind mounts.
   This is the residual privilege that `docs/ROOTLESS_DOCKER.md`
   discusses as the v0.4 mitigation.
2. **A bug in tecnativa's filter logic itself.** The proxy is now
   in the trusted path. The image is pinned at `0.2.0`; bumping is
   one line in the compose file when a fix is needed.
3. **The acceptance probe runs as `--user 0`** inside the worker
   so it can read `/proc/self/mountinfo` and shell out cleanly.
   The real executor code path runs as the worker process user;
   v0.3 does not change *who* the worker runs as.
4. **`pub_network` is still created in `traefik` mode**, even
   though the forwarder isn't used in that mode. Carry-over from
   PR #5 Devin Review comment, deferred to v0.4 per scope.

## Recommendation

A single **supervised smoketest repo task** (planner → frontend →
QA → AWAITING_APPROVAL → human approval → backend → security →
PR) against a **scratch repository** is now safe to attempt under
the same operator-CIDR-only firewall posture, with
`SANDBOX_EXECUTOR=docker` flipped on. Do NOT flip the executor
mode or run the smoketest until the user replies with the verbatim
phrase `approve real project tasks`.

The smoketest itself should still be a scratch repo (not a real
project repo) so the human-in-the-loop has time to confirm the
sequence behaves as documented before connecting any real code to
the platform.
